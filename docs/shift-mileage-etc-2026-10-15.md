# Shift mileage / ETC bridge — source checkpoint

Branch codex/suite-equipment-entry-20261012, based on 6746a62. Unrelated local generated SSO protocol change is excluded. No APK built/installed.

Root cause: final arrival passes distance traveled to finalizeArrival, but ActionCardRow stored that distance under wellbuilt-last-odometer. ShiftStartModal then prefilled it as an absolute starting odometer; blank starts also failed to clear the old per-shift key. The old keys are no longer read. Optional typed starting odometers are bound to company, driver and the successfully claimed Suite shift under a versioned key; blank values and other shifts cannot restore an old reading. Logout/account cleanup includes the new key. Trip distance is never promoted to a starting odometer.

New read-only getMileage bridge call uses the existing signed ETC provider port and fresh request echo validation. The ETC companion change captures a monotonic accepted-GPS-distance counter when the bound Suite shift starts, then returns its delta only for the matching open ETC shift with fresh, uninterrupted GPS evidence. It does not parse the displayed odometer or recompute GPS/HOS. Unavailable/older ETC is an honest manual fallback. The arrival modal labels ETC GPS distance, permits explicit manual override, and sends whole-mile shift distance through the existing close contract. If a true starting odometer was typed for this shift, manual override accepts the ending odometer and calculates distance; otherwise it asks directly for shift miles. Retained retry values remain distances, not ending odometers. DVIR/JSA/paperwork gates remain in place.

Full typecheck retains existing AppSwitcher/SignaturePad/etc diagnostics, none in changed mileage/UI files. Requires updated ETC and Suite together plus a fresh-shift device test; existing shifts without a captured counter baseline use manual entry.
